# 屋台にのきち レジアプリ 設計書

## 1. このアプリの目的

屋台「にのきち」でステーキ（1300円）ほか最大3品を販売する際に使う、スマホ/タブレット用のアプリ。

**このアプリの中心は会計ではなく「待っているお客様と注文を結びつけること」である。**
会計機能はその付随物として設計する。

### 解決する問題（優先順）

1. **商品の渡し間違い** — 焼き上がったステーキを誰に渡すべきか分からなくなる
2. **会計の取り違え** — 誰がまだ払っていないか分からなくなる
3. **焼き忘れ・渡し忘れ** — 混雑時に注文が記憶から落ちる
4. **売り切れ宣言のタイミングのずれ** — 受けたのに出せない／早く締めすぎて売り逃す
5. **撤収後にレジ金と売上が合わない**
6. **次回の仕込み量が勘になる**

根本原因は「服装などの記憶で客を識別していること」。記憶は、客が動く・上着を脱ぐ・似た服装が並ぶと壊れ、しかも混雑時（＝記憶の負荷が最大の時）に壊れる。

## 2. 前提条件

| 項目 | 内容 |
|---|---|
| 商品数 | 3品（ステーキ1300円＋最大2品）。**現地で名前・価格を編集できること** |
| 端末 | 1台（スマホ or タブレット）。これが唯一の正データ |
| 支払い | **現金のみ** |
| 会計タイミング | **先払い**（注文を受けたその場で会計） |
| オペレーション | 2人（調理と接客を分担）。端末は接客側が持つ |
| ピーク時の待ち | **7組以上**、焼き時間は長め |
| 番号札 | **配らない**（物理的に配る物を増やさない方針） |
| ネットワーク | 期待しない。**オフラインで完全に動作すること** |

## 3. 現場制約と設計への反映

| 制約 | 設計 |
|---|---|
| 手が汚れる・グローブ | ボタンは指1本で確実に押せるサイズ。確認ダイアログを置かず、代わりに1タップの取り消しを用意 |
| 直射日光 | 高コントラストのライトテーマ。薄いグレー文字は使わない |
| 電波が弱い/無い | PWA＋端末ローカル保存。クラウド必須にしない |
| 行列が常にある | 1件の注文登録＋会計を最小タップで完了させる |
| 片手操作 | 主要操作は画面下半分に配置 |
| バッテリー | 画面が常時点灯に近くなる前提。重いアニメーションを置かない |

## 4. 運用フロー（先払い・2人オペ）

```
接客側                                        調理側
──────────────────────────────────────────────────────
① 注文を聞く
② 商品ボタンをタップ（連打で数量増加）
③ お名前を伺い、カタカナで入力
   ├ 同名が待ち行列にいれば、特徴タグを1〜2タップ
   └ 名乗りたくない客は名前を空にして特徴タグのみ
④ 「○分ほどお待ちいただきます」と案内（アプリが算出）
⑤ 預かり金額を入力 → お釣りを特大表示 → 確定
                                            ⑥ キューを見て焼く（先頭から）
⑦ 焼き上がったら名前で呼ぶ
   「やまださん、お待たせしました」
⑧ 渡す直前に注文内容で突合
   「ステーキ2つですね」
⑨ [渡した] をタップ
```

名前を聞くタイミングを商品選択の直後に置くのは、④の待ち時間案内と同じ発話の流れに乗せられるため。お釣りを渡しながら端末を操作させない。

## 5. 識別方式（本設計の中核）

### 5.1 なぜ名前か

| 識別子 | 情報量 | 客が覚えているか | 採否 |
|---|---|---|---|
| 番号（口頭のみ） | 高 | 覚えない | ✕ 札を配らない以上成立しない |
| 注文内容 | 低（3品） | 完璧 | △ 7組待ちでは重複が常態 |
| 服装の記憶 | 中 | — | ✕ 現に壊れている |
| **お名前** | **高** | **100%** | **◎ 採用** |

名前は情報量が高く、かつ客が絶対に覚えており、呼ばれたとき確実に反応する唯一の鍵。配る物がゼロなので番号札を使わない方針と矛盾しない。

### 5.2 3層構造

- **第1層 — 名前**：呼び出しの鍵
- **第2層 — 注文内容**：渡す直前の突合。第1層をすり抜けた取り違えをここで止める
- **第3層 — 特徴タグ**：同名が待ち行列に並んだ時のみ記録

### 5.3 段階的識別（入力コストを例外時だけに寄せる）

注文登録時、アプリは待ち行列内の同名を判定する。

- ユニークなら → 追加入力を一切求めない
- 衝突したら → 「⚠ さとうさんが2組待っています」と表示し、特徴タグを促す

**常に特徴を入力させる設計にしてはいけない。** 忙しい時に必ずサボられ、機能が死ぬ。衝突時だけなら運用が守れる。

### 5.4 特徴タグ

自由入力ではなく固定グリッドから選ぶ（2タップで確定）。

- 色：`黒` `白` `赤` `青` `緑` `黄` `茶` `グレー` `ピンク` `紫`
- 種類：`パーカー` `Tシャツ` `シャツ` `ジャケット` `帽子` `ワンピース`
- 属性：`2人` `3人以上` `家族` `子供連れ`

写真撮影は採用しない（客の無断撮影は信用を失う）。

## 6. 画面設計

### 6.1 注文・会計（接客側のメイン）

```
┌────────────────────────────────┐
│  待ち 7組 ／ ステーキ あと3食   │  ← 常時ヘッダー
│  （うち待ち確保 2食）           │
├────────────────────────────────┤
│  ┌──────────┐  ┌──────────┐    │
│  │ ステーキ  │  │  ○○○    │    │  ← 巨大ボタン。連打で数量増加
│  │  1300円   │  │   600円  │    │
│  │    ×2     │  │          │    │
│  └──────────┘  └──────────┘    │
│                                 │
│  合計  2,600円                  │
│  お名前 [ ヤマダ        ]       │
│  ⚠ 同名が待っています → 特徴を記録│
│                                 │
│  預かり [1000][2000][5000][10000]│
│  ───────────────────────────    │
│       お釣り  2,400円            │  ← 特大
│                                 │
│  [        確定（約20分）       ] │
└────────────────────────────────┘
```

### 6.2 待ち行列（キュー）

```
┌──────────────────────────────────┐
│ ▼ 次に渡す                        │  ← 先頭は常に画面上部に固定
│ ③ やまだ さん     ステーキ ×2     │
│    ⏱ 12:20  ● 目安超過            │
│    🏷 黒パーカー・男性             │  ← 衝突時のみ表示
│              [   渡した   ]       │
├──────────────────────────────────┤
│ ④ さとう さん     ステーキ ×1     │
│    ⏱ 8:05   ◉ 焼成中              │  ← キュー先頭N組は焼成中と見なす
│              [   渡した   ]       │
├──────────────────────────────────┤
│ ⑤ すずき さん     ステーキ ×1 ＋○○│
│    ⏱ 3:40   ○ 待機                │
└──────────────────────────────────┘
```

7組以上がスクロールするため、**「次に渡すべき1件」は常に最上部に固定表示**する。
経過時間を出すだけで焼き忘れ・渡し忘れも同時に潰せる。目安超過でカードの色が変わる。

2人オペなので、端末はスタンドに立てて調理側の視界にもキューが入る角度に置くことを前提にする。

### 6.3 今日の状況

売上合計 / 商品別の点数 / 残数 / 時間帯別の棒グラフ / 現金残高の照合（準備金＋売上＝レジ内現金）。

### 6.4 設定

商品名・価格・用意数・焼き時間目安の編集、出店の開始/終了、閉店時刻の設定、データ書き出し（CSV / JSON）。

## 7. データモデル

```ts
type Event = {            // 出店（1日 or 1イベント）
  id: string
  name: string            // "○○祭り"
  date: string            // "2026-10-18"
  closeAt?: string        // 閉店予定時刻。受付停止判断に使う
  cashFloat: number       // 釣り銭準備金
  openedAt?: number
  closedAt?: number
}

type MenuItem = {         // ★Event ごとにコピーを持つ（マスタを直接書き換えない）
  id: string
  eventId: string
  name: string            // "ステーキ"
  price: number           // 1300（税込）
  prepared: number        // 用意数（食）
  soldOut: boolean        // 手動の売り切れフラグ
  cookSeconds: number     // 焼き時間の目安
  sortOrder: number
}

type Order = {
  id: string
  eventId: string
  seq: number             // 当日の通し番号
  lines: {                // ★名前と価格をスナップショット
    itemId: string
    name: string
    price: number
    qty: number
  }[]
  total: number

  // 会計（先払いなので必ず存在する）
  payment: {
    method: 'cash'
    received: number      // 預かり
    change: number        // 釣り
    paidAt: number
  }

  // 識別
  label: string           // 客が名乗った名前（カタカナ）。空可
  tags: string[]          // 衝突時のみ ["黒", "パーカー"]

  // 状態
  status: 'waiting' | 'done' | 'voided'
  createdAt: number
  handedAt?: number       // 渡した時刻。待ち時間推定の実測値になる
  voidedAt?: number
  voidReason?: string
}
```

### 設計上の要点

- **価格と商品名は出店ごと・注文ごとにスナップショットする。** 現地で「今日は1200円にする」と変更しても過去の売上が壊れない。「現地で編集できる」を安全に成立させるための要件。
- **取り消しは論理削除（`voided`）。** 物理削除すると「レジ金が合わない」の原因追跡が不可能になる。
- `status` に `cooking` を持たせない。FIFO なのでキュー先頭N組（N＝同時に焼ける枚数）を焼成中と見なせば追加タップ0で導出できる。調理側に操作を増やさない。

## 8. 待ち時間推定と受付停止

### 待ち時間

グリルの容量などをモデリングしない。**実測から自己校正する。**

```
平均提供間隔 = 直近5件の handedAt の差分の中央値
推定待ち時間 = 自分より前の待ち組数 × 平均提供間隔
```

実測データが無い営業開始直後のみ `cookSeconds` をフォールバックに使う。使うほど精度が上がる。

### 残数

```
今受けられる残数 ＝ 用意数 － 渡し済み － 待ち行列で確保済み
```

**待ち行列の分を引かないと売り切れ宣言が必ず遅れ、「受けたのに出せない」が起きる。**
画面には `あと3食（うち待ち2食）` のように両方出す。0 になった商品は自動で売り切れ表示にする。

### 受付停止の警告

`閉店予定時刻 － 現在時刻 < 推定待ち時間` になったら「受付停止を検討」を表示する。

## 9. 技術スタック

| 層 | 選択 | 理由 |
|---|---|---|
| UI | React + TypeScript | 状態が素直に書ける |
| ビルド | Vite | 軽量・高速 |
| スタイル | Tailwind CSS | 巨大ボタン・高コントラストの調整が速い |
| 配信形態 | **PWA**（vite-plugin-pwa） | ホーム画面に追加してフルスクリーン起動。オフライン動作 |
| 保存 | **IndexedDB**（Dexie） | 営業中に消えない。件数が増えても耐える |
| ホスティング | Vercel または GitHub Pages | 無料・HTTPS（PWA要件） |
| バックエンド | **v1では無し** | 電波が無い現場で死なないことを優先 |

## 10. 非機能要件

### データ保全（最優先）

売上データの消失は致命的。

- 会計確定のたびに IndexedDB へ同期書き込み
- 営業終了時に CSV / JSON の書き出しを**必ず通る導線**に置く
- 端末・ブラウザを固定する運用（プライベートブラウズでは使わない）を README に明記

### オフライン

Service Worker で全アセットをプリキャッシュ。初回起動以降、ネットワークに一切依存しない。

## 11. スコープ外（v1で作らないもの）

意図的に作らない。これらは屋台のレジにおいてノイズになる。

- 顧客管理・ポイント・会員
- 在庫発注・原価管理
- キャッシュレス決済（現金のみ）
- レシート印刷
- 複数端末の同期（将来、閲覧専用の2台目を足す余地だけ設計に残す）
- 客の写真撮影による識別
- 税率の内訳表示（税込価格で記録し、必要時に集計で計算）
